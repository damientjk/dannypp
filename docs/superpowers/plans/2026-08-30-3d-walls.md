# 3D Room Walls Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the flat, synthetically-shaded wall tile every room currently uses with a real, per-theme 2-row wall (a "cap" row + a "base" row) cropped from the asset pack's dedicated wall sheet, so walls read as having actual height instead of a flat painted band.

**Architecture:** Every room's back wall (the wall opposite its door, where the window already lives) grows a second tile row that sits just outside the room's existing footprint. The room's interior size, desk positions, and decor are untouched -- only the map's overall canvas grows by 2 tile rows (1 for each room row's cap) to make room for it. Each of the 6 rooms gets its own 2-row wall texture (cap + base) plus 2 window-composited variants of the base row, picked to match its floor theme, replacing the single global wall texture + hand-coded gradient hack every room currently shares.

**Tech Stack:** Python (PIL) asset-generation scripts, no runtime/engine code changes -- `TiledMapRenderer.ts` reads tile dimensions from `map.json` directly and has no hardcoded map size.

**Spec:** No separate spec doc. This is a bounded follow-on to `docs/superpowers/specs/2026-08-29-room-theming-design.md`, scoped and approved in-chat on 2026-08-30 (short design presented, user chose the two-row/real-depth option over a texture-only swap).

## Global Constraints

* Room interior size, desk positions, decor positions, and collision behavior for existing interior tiles must not change -- only wall rendering and overall canvas height change.
* No engine/runtime TypeScript changes -- confirmed `TiledMapRenderer.ts`, `WorldCanvas.tsx`, `agentSim.ts` have no hardcoded map width/height; they read `map.json` at runtime. If a task discovers otherwise, stop and flag it -- that would be new information contradicting this constraint.
* `generate-world-map.py`, `generate-world-tileset.py`, and `generate-room-decor.py` must stay in sync on room geometry and GID numbering by importing shared values/functions from `room_layout.py` -- never hardcode the same number in two files (existing repo convention, see room_layout.py's own docstring).
* All 3 generator scripts are run via `py <script>.py` (not `python3` -- broken stub on this machine) from `apps/web/scripts/`.
* No pytest/test framework exists for these Python scripts -- verification is: script runs without an `AssertionError`, the regenerated `map.json`/`tileset.png` look correct on visual inspection, and the existing Vitest suite (`npm run test -w @launchpad/web`) still passes (it uses self-contained mock map fixtures, not the real generated files, so it is not expected to need edits -- confirmed by grep, no test imports `map.json`/`tileset.png`).

```python
def shade_wall(tile):
    """Synthesized highlight/shadow coping band so the flat Room_Builder
    wall block reads as a wall with height. Unchanged from the original
    script -- see its docstring for why this is synthesized rather than
    found (no 32x32 pre-shaded wall set exists in the pack)."""
    shaded = tile.copy()
    px = shaded.load()
    w, h = shaded.size
    top_band, bottom_band = 7, 5
    for y in range(h):
        if y < top_band:
            factor = 1.18
        elif y >= h - bottom_band:
            factor = 0.72
        else:
            continue
        for x in range(w):
            r, g, b, a = px[x, y]
            if a == 0:
                continue
            px[x, y] = (min(255, int(r * factor)), min(255, int(g * factor)), min(255, int(b * factor)), a)
    return shaded
```

## Amendment (2026-08-30, after Task 4): the reference-image gable/cornice look

After Tasks 1-4 shipped (flat 2-row cap wall), the user provided two reference
images showing the actual look they want: each room's **back wall** (the wall
opposite the door — already the one wall this plan singles out for special
treatment) should carry a tall, ornate, pillared cornice with a peaked gable
at its center, tapering the wall's silhouette upward — not just a taller flat
band. The user's own framing: *"the walls that bound the room at the bottom
tend to have thinner walls if you notice, and walls at the top have height
creating that illusion, try and keep that effect"* — i.e. within any one
room, the far/back wall gets height, the near/door wall stays thin. That is
exactly the existing back-wall-only cap design from Tasks 1-4; only the CAP
TEXTURE itself needs to change, from a flat tile to a real gable/cornice
graphic.

Source investigation (done in-chat before writing these tasks): the asset is
`moderninteriors-win/1_Interiors/32x32/Room_Bulder_subfiles_32x32/Room_Builder_3d_walls_32x32.png`,
an 8-tile-wide repeating composition per color (pillars flanking a central

## Amendment 4 (2026-08-30, after Task 8 shipped and merged): the cap tile's own texture undermined the whole effect

After Task 8 landed, the user reported (with a live screenshot) that the top-row rooms' walls still didn't look taller, and the corner wedge wasn't visible. Two prior investigations (both live, hard-reloaded, network-verified Playwright checks) confirmed the CODE was doing exactly what Tasks 1-8 specified -- so this amendment is not a design change, it's a previously-undiagnosed rendering bug the design was never able to surface because nobody checked the actual composited tileset bytes.

Root cause, found by pixel-sampling the live canvas and then the committed `tileset.png` directly (not a reference image, not a code read -- the actual shipped asset): the "cap" tile every top-row room uses (`Room_Builder_Walls_32x32.png`, row `2*wall`, picked in Task 1) has a pale/white decorative trim stripe baked into its top ~12px (a "ceiling molding" look, fine for an interior wall segment, wrong for the outermost edge of this game's wall stack). That pale stripe sits directly against the canvas's blank background at the map's very top edge, visually softening the wall's silhouette right where the added height was supposed to read -- and Task 8's corner wedge, which partially overlaps this same stripe, loses contrast there too. This was flagged once, in Task 4's report, as "confirmed source art, not a bug" -- correct on the narrow question asked, but the consequence (the entire point of the cap row is undermined) was never connected until now.
